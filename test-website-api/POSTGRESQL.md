# Local PostgreSQL setup (Windows)

The .NET 8 API now uses Npgsql.EntityFrameworkCore.PostgreSQL 8.0.11 with EF Core
8.0.11. The Angular 20 API routes and response shapes are unchanged. Provider
compatibility: https://www.nuget.org/packages/Npgsql.EntityFrameworkCore.PostgreSQL/8.0.11

On October 26, 2026, the PostgreSQL migration was applied to the local
`sawftware_games` database after confirming it had no public tables. The SQL Server
Express database was never modified or deleted. You chose to start PostgreSQL
empty, so existing SQL Server accounts were not copied; sign up again locally.

## Credentials

Run from this backend directory:

```powershell
.\Configure-Postgres.ps1
```

Enter the connection string at the hidden prompt, using your PostgreSQL login:

```text
Host=localhost;Port=5432;Database=sawftware_games;Username=YOUR_LOGIN;Password=YOUR_PASSWORD
```

This is already configured on this PC. The helper stores the connection using
.NET user secrets under ID `test-website-api-local-postgresql`, outside the
repository. It passes the value through stdin rather than command arguments.
User secrets are local development storage, not encrypted credential storage.
Do not copy the secrets file into the project or paste credentials into Git,
appsettings, launchSettings, or this documentation. For passwords containing
connection-string delimiters, use Npgsql connection-string quoting.

An alternative is the process environment variable
`ConnectionStrings__TestWebsiteDb`, populated through your preferred local secret
manager or a hidden prompt. Environment variables override user secrets. The app
fails with a setup message if no connection string is supplied. ASP.NET Core loads
user secrets automatically in the Development environment.

## Run

In the backend directory:

```powershell
dotnet tool restore
dotnet restore
dotnet build
dotnet run --launch-profile http
```

The existing Angular client calls `http://localhost:5014`. In a separate terminal:

```powershell
cd ..\test-website
npm start
```

Open `http://localhost:4200`; Swagger is at `http://localhost:5014/swagger`.
The existing HTTPS profile is also available with `dotnet run --launch-profile https`.
Trust the local development certificate with `dotnet dev-certs https --trust` if
using HTTPS. Cookie settings remain unchanged: the authentication cookie has
`Secure`, `HttpOnly`, and `SameSite=Lax`. Verification checks cookie issuance;
browser cookie handling depends on the client's HTTP/HTTPS configuration.

## Migrations and verification

The active migration is `20261026121954_InitialPostgreSql`. It creates `Users`
with an `integer GENERATED BY DEFAULT AS IDENTITY` key and required `text`
columns. `Migrations/InitialPostgreSql.sql` contains the SQL for review.
The original SQL Server migration and snapshot are preserved in
`Migrations/SqlServerArchive` with `.cs.txt` extensions so neither the compiler
nor EF tooling treats them as active code or overwrites the archived snapshot.
Do not apply the old SQL Server migrations to PostgreSQL.

For a new empty PostgreSQL database, configure its connection first, inspect it,
then apply the active migration:

```powershell
$env:ASPNETCORE_ENVIRONMENT = 'Development'
dotnet ef database update
```

The application does not automatically create or migrate a database on startup.
The PostgreSQL login needs schema creation privileges to apply migrations and
table/identity-sequence permissions to run the API. No superuser role is required.

To check connectivity and migration status without changing application data:

```powershell
dotnet run --project Verification
```

To run the API smoke checks against the configured database:

```powershell
dotnet run --project Verification -- --api
```

For an inspected, empty target that still needs its migration:

```powershell
dotnet run --project Verification -- --apply-migrations --api
```

The verification tool uses a private API instance on `127.0.0.1:15014`. It checks
signup, generated identity, case-insensitive duplicate rejection and login,
wrong-password and missing-user responses, required input validation, Unicode
round trip, password hashing, user projection, cookie issuance, and Angular's
credentialed CORS preflight. Its temporary account is deleted and its API process
stopped afterward. PostgreSQL identity sequences advance during these checks;
gaps are expected. Run verification as your normal Windows user so local secrets
and Windows-protected authentication keys can be accessed.

## Compatibility review and limits

- The API uses EF LINQ; no raw SQL, stored procedures, SQL defaults, computed
  columns, GUID, date/time, or explicit SQL Server types exist outside the archived
  migration. The C# empty-string initializers remain application defaults.
- SQL Server `int`, `nvarchar(max)`, and identity annotations became PostgreSQL
  `integer`, Unicode `text`, and Npgsql identity annotations.
- PostgreSQL text equality is case sensitive. Signup and login explicitly compare
  lowercase email values, preserving case-insensitive matching for ordinary email
  addresses and retaining the entered spelling in responses. This is not a full
  emulation of every SQL Server collation's accent, locale, or trailing-space rules.
- Password hashes and API response fields remain unchanged. Email uniqueness still
  uses the existing application-level check; concurrent-signup behavior is unchanged.
- `Controllers/BugController` is an existing unfinished file without a `.cs`
  extension and is not compiled. The Angular feedback page calls `/api/feedback`,
  which had no backend endpoint before this migration. These unfinished features
  were not database operations available to migrate or verify.
- Backend build and Angular production build passed on this PC. Actual PostgreSQL
  connectivity, migration application, and the smoke checks passed against
  `sawftware_games`. Raspberry Pi configuration and deployment are deferred.

`bin` and `obj` were already tracked in this repository. The new `.gitignore`
excludes future untracked build outputs and local environment files, but cannot
untrack existing files. Review the source changes separately from generated build
artifacts before committing; existing local changes were retained.
